\section{Cel i zakres przedsięwzięcia}

\subsection{Wstęp}
Celem projektu jest opracowanie aplikacji webowej do proponowania spersonalizowanych prezentów dla osób na podstawie podanych linków do ich mediów społecznościowych, a także podanych zainteresowań podczas wywiadu z chatbotem. Na podstawie danych system generuje przykładowe propozycje prezentów, aby następnie wyszukać je w zintegrowanych serwisach sklepowych i zwrócić linki do ofert użytkownikowi.

\subsection{Cel główny}
Stworzenie użytecznego, szybkiego i bezpiecznego narzędzia wspierającego proces znajdowania prezentu poprzez:
\begin{itemize}
    \item automatyczne wydobycie i analizę cech osoby na podstawie mediów społecznościowych (OSINT),
    \item interaktywny chat z agentem AI w celu zebrania dodatkowych informacji,
    \item generowanie trafnych propozycji prezentów na podstawie uzyskanych danych,
    \item proponowanie konkretnych ofert produktów ze sklepów internetowych (agregacja).
\end{itemize}

\subsection{Zakres projektu}
\textbf{Co wchodzi w zakres projektu:}
\begin{itemize}
    \item interfejs webowy do wprowadzania linków do publicznych profili społecznościowych i prowadzenia chatu z użytkownikiem,
    \item moduł parsowania i ekstrakcji jedynie publicznych, jawnych danych z podanych profili,
    \item generowanie propozycji prezentów dla wybranej osoby,
    \item propozycja ofert prezentów ze sklepów internetowych (OLX, Allegro, eBay, Amazon),
    \item filtry wyników (np. po cenie, kategorii).
\end{itemize}

\textbf{Co nie wchodzi w zakres projektu:}
\begin{itemize}
    \item automatyczne dokonywanie zakupów ani płatności,
    \item zbieranie prywatnych danych wymagających logowania,
    \item generowanie treści graficznych produktów (korzystamy z gotowych zdjęć ofert).
\end{itemize}

\subsection{Cele biznesowe i techniczne}
Z biznesowego punktu widzenia projekt ma na celu skrócenie czasu potrzebnego na znalezienie prezentu z kilkunastu godzin do kilku minut oraz zwiększenie trafności upominków. Z technicznego punktu widzenia celem jest weryfikacja możliwości wykorzystania modeli LLM do sterowania procesem wyszukiwania i selekcji ofert (Agentic Commerce) oraz integracja wielu źródeł danych w czasie rzeczywistym.

\section{Założenia wstępne}

\subsection{Założenia technologiczne}
\begin{itemize}
    \item \textbf{Frontend:} React (Single Page Application)
    \item \textbf{Backend:} NestJS (Node.js framework)
    \item \textbf{Baza danych:} PostgreSQL
    \item \textbf{Komunikacja:} RabbitMQ (kolejkowanie zadań), REST API, SSE
    \item \textbf{Integracje zewnętrzne:}
    \begin{itemize}
        \item API mediów społecznościowych (poprzez proxy/scraping)
        \item API e-commerce: OLX, Amazon, eBay, Allegro, Okazje (Sandbox / scraping)
        \item OpenAI API / Google Gemini API (modele językowe)
    \end{itemize}
    \item \textbf{Hosting:} VPS, obsługa HTTPS
\end{itemize}

\subsection{Założenia projektowe i ograniczenia}
\begin{itemize}
    \item Przetwarzane są wyłącznie dane publicznie dostępne (OSINT).
    \item System nie obsługuje płatności ani finalizacji transakcji (przekierowanie do sklepu).
    \item Dane osobowe nie są wykorzystywane w celach marketingowych. Historia wyszukiwań i zapisane produkty są przechowywane wyłącznie dla zalogowanych użytkowników w celu zapewnienia ciągłości sesji.
    \item Projekt ma charakter edukacyjno-prototypowy (MVP).
\end{itemize}

\subsection{Iteracja 1: POC (Proof of Concept)}
Celem pierwszej iteracji było sprawdzenie, czy najważniejsze ryzyka technologiczne są rozwiązywalne:
\begin{itemize}
    \item przygotowanie \textbf{NestJS boilerplate} z obsługą zdarzeń (issue: \textit{"NestJS boilerplate z zmockowanymi eventami"}),
    \item \textbf{Gift Search POC} – przetestowanie możliwości wyszukiwania prezentów w zewnętrznych serwisach,
    \item \textbf{POC scrapera Facebooka, Instagrama i Tiktoka} – weryfikacja, czy da się zbudować moduł OSINT,
    \item uruchomienie podstawowego \textbf{frontendu} ("set up basic frontend project"),
    \item przygotowanie pierwszych \textbf{diagramów}: C4, BPMN, projekt premise.
\end{itemize}
Rezultatem iteracji POC było potwierdzenie, że analiza profili, komunikacja zdarzeniowa i podstawowe wyszukiwanie produktów są możliwe w przyjętym stosie technologicznym. Na tym etapie powstały również pierwsze makiety interfejsu (Figma) oraz wstępny podział odpowiedzialności w zespole (backend, frontend, DevOps).

\subsection{Iteracja 2: Design}
Druga iteracja skupiła się na doprecyzowaniu architektury i modelu domeny:
\begin{itemize}
    \item utworzenie \textbf{diagramów C4} (wersja ogólna i wersja mikroserwisowa),
    \item przygotowanie \textbf{diagramu klas} oraz \textbf{diagramu BPMN} opisującego przepływ procesu,
    \item doprecyzowanie podziału na mikroserwisy i kontraktów między nimi,
    \item konfiguracja środowiska developerskiego i CI.
\end{itemize}
Na koniec iteracji Design powstał spójny model architektoniczny, który został wykorzystany przy budowie MVP.

\subsection{Iteracja 3: MVP}
Trzecia iteracja miała na celu dostarczenie \textbf{działającego MVP} aplikacji:
\begin{itemize}
    \item wyodrębnienie mikroserwisów: \texttt{gift-ideas-microservice}, \texttt{reranking-microservice}, \texttt{fetch-microservice},
    \item integracja chatu z architekturą zdarzeniową ("EPIC: integrate chat POC with microservices setup"),
    \item dodanie widoków \textbf{frontendowych}: home, stalking, chat, rekomendacje,
    \item implementacja \textbf{historii czatu} oraz \textbf{historii rekomendacji prezentów},
    \item dodanie \textbf{ulubionych produktów}, filtrowania i sortowania,
    \item pierwsza wersja \textbf{systemu rerankingu} i integracja z platformami e-commerce.
\end{itemize}
W trakcie iteracji MVP powstał też \textbf{landing page} oraz logotyp projektu. Celem biznesowym było udostępnienie wersji, która rozwiązuje podstawowy problem użytkownika: wygenerowanie sensownych propozycji prezentów w jednym miejscu.

Przykładowo, podczas jednego z wewnętrznych testów MVP okazało się, że standardowe wyszukiwanie produktów zwraca wiele duplikatów oraz ofert zupełnie niepasujących do profilu obdarowywanej osoby (np. części zamienne zamiast gotowych prezentów). To konkretne doświadczenie doprowadziło do zaprojektowania dedykowanego modułu rerankingu opartego na AI, który odfiltrowuje szum i eksponuje najbardziej trafne propozycje.

\subsection{Iteracja 4: Deploy}
Ostatnia iteracja skupiła się na przygotowaniu systemu do beta-testów i wdrożenia produkcyjnego:
\begin{itemize}
    \item dodanie \textbf{logowania i autoryzacji} (Google OAuth, uprawnienia, odświeżanie tokenów),
    \item rozbudowa \textbf{panelu użytkownika} oraz \textbf{panelu administratora},
    \item dopracowanie \textbf{UX/UI} (animacje chatu, lepszy layout na desktopie, landing page),
    \item optymalizacje \textbf{rerankingu} (usuwanie duplikatów, pararelizacja oceniania, pętla regeneracji propozycji),
    \item \textbf{tłumaczenie} aplikacji na język polski,
    \item przygotowanie \textbf{deploymentu} (CI/CD, migracje bazy danych, health-checki).
\end{itemize}
W tej iteracji skoncentrowano się również na przygotowaniu aplikacji do testów z realnymi użytkownikami oraz zbieraniu feedbacku (gwiazdki, formularze opinii). Pojawiły się też mechanizmy refinementu (dopytywanie o lepsze prezenty na podstawie wcześniejszych wyborów) oraz pytanie o budżet przed rozpoczęciem wywiadu.

\subsubsection*{Szczegółowy opis przypadków użycia}
Powyższa lista U1--U6 przedstawia skrótowo najważniejsze funkcje systemu z perspektywy biznesowej. Poniższy opis rozwija je w postaci scenariuszy U1--U7 (np. U1--U4 składają się na jeden główny przepływ ,,Szukanie prezentu'', a U5 został rozbity na osobne przypadki: ulubione, filtrowanie i korzystanie z historii). Opis ma charakter biznesowy i koncentruje się na intencjach użytkownika, danych wejściowych/wyjściowych oraz alternatywnych ścieżkach; diagram pozostaje bez zmian.

\textbf{U1. Szukanie prezentu (główny przepływ).}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Użytkownik jest zalogowany. Ma opcjonalnie linki do profili społecznościowych oraz budżet.
    \item \textbf{Scenariusz główny:} Użytkownik podaje linki i budżet, następnie przechodzi krótki wywiad z chatbotem. Na podstawie profili i odpowiedzi system buduje profil odbiorcy, generuje pomysły na prezenty i zwraca listę realnych ofert z wielu sklepów. Oferty pojawiają się stopniowo, bez czekania na wszystkie źródła.
    \item \textbf{Przebiegi alternatywne:} Brak linków — system opiera się wyłącznie na wywiadzie. Część sklepów niedostępna — lista jest niepełna, ale nadal rośnie w miarę dostępności. Użytkownik pomija część pytań — system działa na mniejszym kontekście, później można doprecyzować. Użytkownik nie jest zalogowany — przed rozpoczęciem wyszukiwania zostaje przekierowany do przypadku U3 (logowanie przez Google).
    \item \textbf{Warunki końcowe:} Użytkownik widzi listę ofert dopasowanych do odbiorcy oraz ma zapisaną sesję do wglądu w historii.
\end{itemize}

\textbf{U2. Dodanie produktu do ulubionych / historii.}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Użytkownik jest zalogowany i ogląda wygenerowane oferty.
    \item \textbf{Scenariusz główny:} Użytkownik oznacza wybrane oferty jako ulubione; może je później zobaczyć w zakładce „Zapisane” lub w historii danej sesji.
    \item \textbf{Przebiegi alternatywne:} Próba zapisania oferty spoza własnej sesji jest blokowana; powtórne zapisanie tej samej oferty nie zmienia wyniku.
    \item \textbf{Warunki końcowe:} Lista ulubionych jest dostępna do ponownego otwarcia oferty lub kontynuacji rozmowy.
\end{itemize}

\textbf{U3. Logowanie przez Google.}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Użytkownik posiada konto Google.
    \item \textbf{Scenariusz główny:} Użytkownik przechodzi proces logowania Google, po którym uzyskuje dostęp do funkcji wymagających konta (historia, ulubione, feedback).
    \item \textbf{Przebiegi alternatywne:} Rezygnacja w trakcie logowania lub błąd uwierzytelnienia — brak dostępu do funkcji konta; użytkownik może spróbować ponownie.
    \item \textbf{Warunki końcowe:} Sesja użytkownika jest aktywna i pozwala korzystać z funkcji powiązanych z kontem.
\end{itemize}

\textbf{U4. Wystaw opinię (feedback).}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Użytkownik jest zalogowany i ma zakończoną sesję wyszukiwania.
    \item \textbf{Scenariusz główny:} Użytkownik ocenia jakość rekomendacji (gwiazdki, komentarz), może załączyć zdjęcia lub wskazać konkretną ofertę. Opinie są widoczne w panelu administratora i mogą wspierać dalsze ulepszenia.
    \item \textbf{Przebiegi alternatywne:} Brak wskazania konkretnej oferty — feedback traktowany jako ogólny. Brak komentarza — zapisywana jest sama ocena.
    \item \textbf{Warunki końcowe:} Opinia zostaje zapisana i może być analizowana przez zespół/administratora.
\end{itemize}

\textbf{U5. Doprecyzuj wyszukiwanie (refinement).}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Użytkownik ma wygenerowaną listę ofert w danej sesji.
    \item \textbf{Scenariusz główny:} Użytkownik wybiera kilka propozycji, które mu się podobają lub nie, i uruchamia kolejną rundę wyszukiwania. System proponuje nowy zestaw ofert na bazie preferencji z poprzedniej rundy.
    \item \textbf{Przebiegi alternatywne:} Brak zaznaczonych ofert — doprecyzowanie nie startuje. Niedostępne źródła — kolejna runda zawiera wyniki z dostępnych sklepów.
    \item \textbf{Warunki końcowe:} Użytkownik otrzymuje dodatkowe, lepiej dopasowane oferty w tej samej sesji.
\end{itemize}

\textbf{U6. Filtruj / sortuj wyniki.}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Są dostępne oferty dla danej sesji.
    \item \textbf{Scenariusz główny:} Użytkownik zawęża listę po cenie, dostawcy, ulubionych lub rundzie wyszukiwania i sortuje wyniki, by szybciej znaleźć właściwy prezent.
    \item \textbf{Przebiegi alternatywne:} Jeśli część źródeł nie zwróciła wyników, filtry działają na dostępnych ofertach; system może sygnalizować ograniczoną liczbę wyników.
    \item \textbf{Warunki końcowe:} Użytkownik widzi zawężoną, posortowaną listę i może podjąć decyzję.
\end{itemize}

\textbf{U7. Panel administracyjny (feedbacki i statystyki).}
\begin{itemize}
    \item \textbf{Warunki wstępne:} Użytkownik posiada rolę administratora.
    \item \textbf{Scenariusz główny:} Administrator przegląda zgromadzone opinie oraz podstawowe statystyki (liczbę opinii, liczbę sesji z opiniami, średnią ocenę), aby monitorować jakość rekomendacji oczami użytkowników.
    \item \textbf{Przebiegi alternatywne:} Brak danych (np. brak feedbacków) — panel wyświetla puste zestawienia, ale pozostaje dostępny.
    \item \textbf{Warunki końcowe:} Administrator ma wgląd w kondycję produktu z perspektywy użytkowników; w ramach MVP panel pełni wyłącznie funkcję raportową (bez bezpośrednich zmian w danych użytkowników).
\end{itemize}

\section{Specyfikacja wymagań na produkt programowy}

Poniższa specyfikacja formalizuje wymagania zidentyfikowane w trakcie kolejnych iteracji i pracy z backlogiem, tak aby można je było jednoznacznie odwzorować w architekturze i implementacji.

\subsection{Wymagania funkcjonalne}
Poniższe wymagania opisują \emph{co} system ma robić z perspektywy użytkownika. Dla każdego ujęto skrócony opis oraz kryteria akceptacji, które pozwalają weryfikować spełnienie wymagania podczas testów.

% Wymagania funkcjonalne zostały zdefiniowane na początku projektu jako oczekiwane możliwości biznesowe systemu.
\paragraph{F1. Zebranie kontekstu o osobie obdarowywanej.}
\begin{itemize}
    \item \textbf{Opis:} System powinien umożliwiać użytkownikowi szybkie przekazanie podstawowych informacji o osobie obdarowywanej (linki do profili społecznościowych, okazja, przybliżony budżet), tak aby dalsze etapy mogły być maksymalnie zautomatyzowane.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Przeciętny użytkownik jest w stanie wypełnić formularz startowy w ciągu jednej wizyty, bez potrzeby sięgania po dokumentację techniczną.
        \item System akceptuje zarówno scenariusz z podaniem linków do profili, jak i scenariusz, w którym użytkownik opiera się wyłącznie na odpowiedziach w wywiadzie.
    \end{itemize}
\end{itemize}

\paragraph{F2. Wykorzystanie danych publicznych (OSINT).}
\begin{itemize}
    \item \textbf{Opis:} System powinien wykorzystywać publicznie dostępne informacje z profili społecznościowych do lepszego zrozumienia zainteresowań i stylu życia obdarowywanej osoby, bez sięgania po dane prywatne.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Dla osób, dla których dostępne są publiczne profile, użytkownicy subiektywnie oceniają rekomendacje jako lepiej dopasowane niż w scenariuszu bez linków (na podstawie zebranych opinii).
        \item Brak dostępu do profilu lub brak linków nie blokuje procesu znajdowania prezentu — użytkownik może nadal przejść pełny flow oparty wyłącznie na wywiadzie.
    \end{itemize}
\end{itemize}

\paragraph{F3. Wywiad z użytkownikiem.}
\begin{itemize}
    \item \textbf{Opis:} System powinien przeprowadzić użytkownika przez krótki, zrozumiały wywiad dotyczący relacji z obdarowywanym, okazji i jego preferencji, tak aby nie wymagać od użytkownika formułowania technicznych zapytań.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Użytkownik otrzymuje serię pytań w naturalnym języku, z możliwością udzielania odpowiedzi tekstowych lub wybierania z sugerowanych opcji.
        \item Po zakończeniu wywiadu użytkownik nie musi ręcznie konfigurować dodatkowych parametrów — system przechodzi do wyszukiwania prezentów automatycznie.
    \end{itemize}
\end{itemize}

\paragraph{F4. Ukryta analiza profilu odbiorcy.}
\begin{itemize}
    \item \textbf{Opis:} System powinien łączyć odpowiedzi z wywiadu i dane publiczne w wewnętrzny profil odbiorcy, używany do podejmowania decyzji przez moduły AI, bez konieczności prezentowania tego profilu użytkownikowi w formie technicznej.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Dla wyraźnie różnych typów odbiorców (np. osoba techniczna vs. artystyczna) generowane listy prezentów różnią się zauważalnie co do charakteru propozycji.
        \item Użytkownicy w badaniach jakościowych potrafią wskazać, które elementy profilu obdarowywanego zostały dobrze uchwycone przez system (na podstawie opisu rekomendacji), mimo że profil jako taki nie jest im wyświetlany.
    \end{itemize}
\end{itemize}

\paragraph{F5. Generowanie listy potencjalnych prezentów.}
\begin{itemize}
    \item \textbf{Opis:} System powinien na podstawie zbudowanego profilu wewnętrznie wygenerować listę możliwych typów prezentów i wykorzystać ją wyłącznie jako etap pośredni przed pokazaniem gotowych ofert.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Użytkownik końcowy widzi jedynie gotowe propozycje produktów; szczegóły wewnętrznej listy pomysłów nie są eksponowane w interfejsie.
        \item Dla tego samego zestawu danych wejściowych lista produktów pozostaje spójna tematycznie (np. wszystkie dotyczą fotografii, gier, gotowania itp.).
    \end{itemize}
\end{itemize}

\paragraph{F6. Znalezienie realnych ofert w sklepach.}
\begin{itemize}
    \item \textbf{Opis:} System powinien przekuć wygenerowane pomysły na konkretne, realne oferty z wielu niezależnych platform sprzedażowych, tak aby użytkownik mógł od razu przejść do zakupu.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Dla typowego scenariusza (z wypełnionym formularzem i wywiadem) użytkownik otrzymuje co najmniej kilkadziesiąt propozycji produktów, pochodzących z co najmniej trzech różnych platform sprzedażowych.
        \item Każda propozycja zawiera minimalny zestaw informacji biznesowych: nazwę, cenę, miniaturę/zdjęcie (jeśli dostępne) oraz link prowadzący do miejsca zakupu.
    \end{itemize}
\end{itemize}

\paragraph{F7. Zawężanie listy i oznaczanie ulubionych.}
\begin{itemize}
    \item \textbf{Opis:} System powinien umożliwiać użytkownikowi zawężenie długiej listy prezentów do kilku najbardziej interesujących pozycji oraz ich oznaczanie jako ulubione, tak aby łatwo wrócić do nich później.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Użytkownik może w intuicyjny sposób ograniczyć listę widocznych prezentów według kilku prostych kryteriów (np. poziomu ceny czy źródła) bez konieczności znajomości składni zapytań.
        \item Użytkownik może oznaczyć wybrane produkty jako ulubione i znaleźć je później w jednym, dedykowanym miejscu w aplikacji.
    \end{itemize}
\end{itemize}

\paragraph{F8. Historia sesji i możliwość powrotu.}
\begin{itemize}
    \item \textbf{Opis:} System powinien zapamiętywać sesje wyszukiwania, aby użytkownik mógł wrócić do poprzednich wyników, przemyśleć je na spokojnie lub kontynuować rozpoczęty wcześniej proces.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Użytkownik widzi listę swoich sesji wyszukiwania z podstawowymi informacjami (nazwa, data, liczba znalezionych prezentów).
        \item Użytkownik może otworzyć ponownie wybraną sesję i zobaczyć te same wyniki, bez konieczności ponownego wprowadzania danych.
    \end{itemize}
\end{itemize}

\paragraph{F9. Opinie użytkowników i wgląd administracyjny.}
\begin{itemize}
    \item \textbf{Opis:} System powinien umożliwiać użytkownikom przekazywanie prostych opinii o jakości rekomendacji, a administratorowi — przeglądanie zanonimizowanych statystyk tych opinii.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Użytkownik może po zakończonej sesji ocenić rekomendacje w prosty sposób (np. skala gwiazdkowa, krótki komentarz).
        \item Administrator ma dostęp do zagregowanych danych (liczba opinii, liczba sesji z opiniami, średnia ocena), pozwalających ocenić jakość rozwiązania na poziomie całego systemu.
    \end{itemize}
\end{itemize}

\subsection{Wymagania niefunkcjonalne}
Wymagania niefunkcjonalne określają \emph{jak dobrze} system powinien realizować funkcje zdefiniowane powyżej. Dla każdego z nich zdefiniowano mierzalne kryteria akceptacji.

\paragraph{NF1. Dostępność i obsługiwane platformy.}
\begin{itemize}
    \item \textbf{Opis:} Aplikacja działa w przeglądarce bez konieczności instalacji dodatkowego oprogramowania, z responsywnym interfejsem dopasowanym do urządzeń desktopowych i mobilnych.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item System jest dostępny w najnowszej stabilnej wersji co najmniej jednej popularnej przeglądarki (np. Chrome) bez zauważalnych błędów blokujących; wsparcie pozostałych przeglądarek jest celem dalszego rozwoju.
        \item Kluczowe scenariusze (U1--U2) są wykonalne zarówno na desktopie, jak i na typowym urządzeniu mobilnym (potwierdzone testami ręcznymi na przynajmniej jednym reprezentatywnym urządzeniu).
        \item Wejście na stronę nie wymaga instalacji pluginów ani rozszerzeń poza standardowo dostępną przeglądarką.
    \end{itemize}
\end{itemize}

\paragraph{NF2. Wydajność i czas odpowiedzi.}
\begin{itemize}
    \item \textbf{Opis:} System powinien w akceptowalnym dla użytkownika czasie reagować na działania, w szczególności podczas wywiadu i wyszukiwania prezentów, przy czym dopuszcza się, że pełne wyniki mogą być dostępne dopiero po kilku minutach.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Po rozpoczęciu wywiadu lub wyszukiwania użytkownik w krótkim czasie widzi wyraźny sygnał, że system pracuje (zmiana widoku, komunikat, pasek postępu) — brak wrażenia, że aplikacja „zawiesiła się”.
        \item W sytuacjach, gdy generowanie pierwszych sensownych rekomendacji może zająć kilka minut, interfejs informuje o tym użytkownika (np. komunikatem typu ,,to może potrwać kilka minut'') oraz prezentuje pasek postępu lub inny wskaźnik.
        \item Pełne wyniki mogą pojawiać się stopniowo, ale użytkownik ma przez cały czas wgląd w postęp (procent, etapy) i może przerwać proces bez utraty już wyświetlonych propozycji.
    \end{itemize}
\end{itemize}

\paragraph{NF3. Bezpieczeństwo i poufność danych.}
\begin{itemize}
    \item \textbf{Opis:} System musi chronić dane użytkowników oraz osoby obdarowywanej, ograniczając się do publicznych danych i zapewniając bezpieczną komunikację.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Cała komunikacja pomiędzy przeglądarką a backendem odbywa się z użyciem protokołu HTTPS (brak mieszanej treści HTTP na stronach aplikacji).
        \item System nie prosi o dane logowania do serwisów społecznościowych obdarowywanej osoby ani nie wykorzystuje prywatnych informacji wymagających logowania.
        \item Użytkownik może w każdej chwili wylogować się; po wylogowaniu dostęp do historii, ulubionych i panelu admina jest zablokowany.
    \end{itemize}
\end{itemize}

\paragraph{NF4. Skalowalność i odporność na obciążenie.}
\begin{itemize}
    \item \textbf{Opis:} Architektura ma umożliwiać skalowanie obciążonych komponentów (np. wyszukiwania ofert, rerankingu) bez wpływu na resztę systemu.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Architektura oraz konfiguracja uruchomieniowa pozwalają na uruchomienie dodatkowych instancji mikroserwisów odpowiedzialnych za wyszukiwanie i reranking bez konieczności modyfikacji interfejsu użytkownika (skalowanie poziome jest możliwe na poziomie infrastruktury).
        \item Awaria pojedynczej instancji serwisu odpowiedzialnego za pobieranie ofert nie blokuje pozostałych funkcji systemu (chat, historia, ulubione nadal działają, choć lista ofert może być niepełna).
        \item System poprawnie obsługuje sytuację, w której jeden z dostawców ofert (np. konkretny sklep) przestaje odpowiadać — użytkownik nadal otrzymuje częściowe wyniki i czytelną informację o ograniczeniu (np. brak ofert z danego źródła).
    \end{itemize}
\end{itemize}

\paragraph{NF5. Obsługa błędów i komunikaty dla użytkownika.}
\begin{itemize}
  
    \item \textbf{Opis:} W przypadku błędów zewnętrznych serwisów, problemów z siecią lub nietypowych danych wejściowych system powinien zachowywać się przewidywalnie i komunikować problem językiem zrozumiałym dla użytkownika.
    \item \textbf{Kryteria akceptacji:}
    \begin{itemize}
        \item Dla typowych błędów (brak wyników, brak odpowiedzi z jednego źródła, niepoprawny link) użytkownik widzi czytelny komunikat w UI, a aplikacja nie zawiesza się.
        \item W przypadku braku jakichkolwiek ofert system sugeruje możliwe działania (np. zmianę budżetu, inny profil, odświeżenie wyszukiwania), zamiast prezentować pustą stronę.
        \item Błędy techniczne (np. wewnętrzne komunikaty serwera) nie są ujawniane bezpośrednio użytkownikowi końcowemu.
    \end{itemize}
\end{itemize}

Powyższy zestaw wymagań funkcjonalnych i niefunkcjonalnych stał się podstawą do opracowania architektury systemu, opisanej szczegółowo w następnej sekcji.

\section{Projekt produktu programowego}

Zdefiniowane wymagania funkcjonalne i niefunkcjonalne zostały odwzorowane w poniższej architekturze mikroserwisowej, obejmującej zarówno warstwę frontendową, jak i zestaw współpracujących usług backendowych.

\subsection{Architektura systemu}
System został zaprojektowany w architekturze mikroserwisowej, co zapewnia skalowalność i separację odpowiedzialności. Komunikacja między serwisami odbywa się asynchronicznie za pośrednictwem kolejki wiadomości RabbitMQ.

Główne komponenty systemu:
\begin{itemize}
    \item \textbf{Frontend (React):} Interfejs użytkownika komunikujący się z backendem przez REST API oraz odbierający aktualizacje w czasie rzeczywistym przez SSE (Server-Sent Events).
    \item \textbf{RestAPI Macroservice} (\texttt{restapi-macroservice}): Brama wejściowa (API Gateway), obsługująca żądania HTTP i przekierowująca je do odpowiednich kolejek.
    \item \textbf{Chat Microservice} (\texttt{chat-microservice}): Odpowiada za prowadzenie wywiadu z użytkownikiem.
    \item \textbf{Stalking Microservice} (\texttt{stalking-microservice}): Realizuje proces OSINT (analiza profili społecznościowych).
    \item \textbf{Gift Ideas Microservice} (\texttt{gift-ideas-microservice}): Generuje abstrakcyjne pomysły na prezenty na podstawie zebranych danych.
    \item \textbf{Fetch Microservice} (\texttt{fetch-microservice}): Agreguje oferty z zewnętrznych platform (OLX, Allegro, Amazon, eBay, Okazje) przy użyciu dedykowanych handlerów per źródło. Działa w wielu instancjach równolegle.
    \item \textbf{Reranking Microservice} (\texttt{reranking-microservice}): Ocenia i filtruje znalezione oferty przy użyciu AI.
\end{itemize}

\subsection{Poziom 3: Komponenty wybranych mikroserwisów}

\subsection{Zastosowane wzorce projektowe}
\begin{itemize}
    \item \textbf{CQRS (Command Query Responsibility Segregation):} Rozdzielenie operacji modyfikujących stan (Command) od zapytań o dane (Query).
    \item \textbf{Event-Driven Architecture:} System reaguje na zdarzenia (np. \texttt{StalkingCompletedEvent}, \texttt{ProductFetchedEvent}), co pozwala na luźne powiązanie komponentów.
    \item \textbf{Asynchronous Request-Reply:} Obsługa długotrwałych procesów bez blokowania wątku głównego.
    \item \textbf{Strategy:} Wybór odpowiedniego algorytmu pobierania danych w zależności od źródła (np. strategia dla OLX vs strategia dla Amazon).
    \item \textbf{DTO (Data Transfer Object):} Ustrukturyzowane obiekty do przesyłania danych między warstwami.
\end{itemize}

\subsection{Algorytm Rerankingu z Weryfikacją (XAI)}
Najważniejszym elementem systemu jest moduł rerankingu, który filtruje oferty niedopasowane do profilu odbiorcy. Tradycyjne wyszukiwanie oparte na prostych frazach tekstowych często zwraca wyniki nieadekwatne (np. akcesoria do konsoli zamiast konsoli). Zaimplementowany algorytm wykorzystuje model LLM (Gemini 2.5) do oceny semantycznej każdego produktu.
Dla każdej oferty model generuje:
\begin{itemize}
    \item Ocenę punktową (0-10) zgodności z profilem odbiorcy.
    \item Tekstowe uzasadnienie decyzji (np. "Odrzucono: Produkt to część zamienna, a nie gotowy prezent").
\end{itemize}
Pozwala to na odfiltrowanie ok. 40\% szumu informacyjnego.

Poniżej przedstawiono fragment systemu promptów definiującego kryteria oceny produktów:

Jak pokazano w Listingu~\ref{lst:reranking}, kryteria oceny produktów są zapisane w postaci czytelnego dla człowieka systemu promptów, który wymusza wyjaśnialne (XAI) decyzje modelu.

\begin{lstlisting}[caption={Fragment systemu promptów dla rerankingu produktów},label={lst:reranking}]
<criteria>
  <relevance priority="highest">
    Czy produkt odpowiada zainteresowaniom i hobby odbiorcy?
  </relevance>
  <lifestyle_fit priority="high">
    Czy produkt pasuje do stylu zycia i codziennej rutyny?
  </lifestyle_fit>
  <preferences priority="high">
    Czy produkt jest zgodny z preferencjami estetycznymi?
  </preferences>
  <occasion priority="medium">
    Czy produkt jest odpowiedni dla danej okazji?
  </occasion>
</criteria>

<scoring>
  1-3: Slabe dopasowanie - produkt nie pasuje do profilu
  4-6: Srednie dopasowanie - moze pasowac, ale nie jest idealny
  7-8: Dobre dopasowanie - produkt dobrze pasuje do profilu
  9-10: Doskonale dopasowanie - idealnie pasuje do profilu i okazji
  
  Wyniki ponizej 5 nie beda widoczne uzytkownikowi.
</scoring>
\end{lstlisting}

\subsection{Orkiestracja zdarzeń w architekturze CQRS}
Centralnym elementem systemu jest handler \texttt{StartProcessingCommand}, który orkiestruje rozpoczęcie całego procesu wyszukiwania prezentu. Po otrzymaniu żądania od użytkownika tworzy sesję chatu w bazie danych, a następnie równolegle publikuje dwa zdarzenia do kolejki RabbitMQ: jedno uruchamia analizę OSINT profili społecznościowych, drugie – wywiad z chatbotem.

Listing~\ref{lst:orchestration} przedstawia uproszczoną implementację tego handlera, podkreślając zasadę: najpierw utrwalenie sesji w bazie, dopiero później emisja zdarzeń do innych mikroserwisów.

\begin{lstlisting}[caption={Orkiestracja zdarzeń przy rozpoczęciu wyszukiwania prezentu},label={lst:orchestration}]
@CommandHandler(StartProcessingCommand)
export class StartProcessingCommandHandler {
  constructor(
    @Inject("STALKING_ANALYZE_REQUESTED_EVENT")
    private readonly stalkingEventBus: ClientProxy,
    @Inject("CHAT_START_INTERVIEW_EVENT")
    private readonly chatEventBus: ClientProxy,
    private readonly chatRepository: IChatRepository,
  ) {}

  async execute(command: StartProcessingCommand) {
    // 1. Najpierw tworzymy sesje w bazie danych
    const chat = await this.chatRepository.create({
      chatId: analyzeRequestedDto.chatId,
      chatName: `Chat ${new Date().toLocaleDateString()}`,
      userId,
    });

    // 2. Dopiero po utrwaleniu emitujemy zdarzenia rownolegle
    this.stalkingEventBus.emit(
      StalkingAnalyzeRequestedEvent.name, stalkingEvent
    );
    this.chatEventBus.emit(
      ChatStartInterviewEvent.name, interviewEvent
    );
  }
}
\end{lstlisting}

\subsection{Strukturyzacja rozmowy przez Tool Calling}
Moduł chatu wykorzystuje mechanizm \textit{tool calling} do wymuszenia strukturyzowanej odpowiedzi od modelu LLM. Zamiast swobodnego tekstu, AI musi wywołać jedno z trzech narzędzi: zadać pytanie z sugerowanymi odpowiedziami, zakończyć wywiad z wygenerowanym profilem, lub oznaczyć nieodpowiednie zapytanie.

Listing~\ref{lst:tools} pokazuje definicję tych narzędzi wraz z odpowiadającymi im schematami Zod, co zapewnia typowaną i przewidywalną współpracę pomiędzy LLM a resztą systemu.

\begin{lstlisting}[caption={Definicja narzędzi AI dla strukturyzacji wywiadu},label={lst:tools}]
export const tools = {
  ask_a_question_with_answer_suggestions: tool({
    description: "Zadaj pytanie z 4 sugerowanymi odpowiedziami",
    inputSchema: z.strictObject({
      question: z.string().min(1),
      potentialAnswers: potencialAnswersSchema,
    }),
  }),
  
  end_conversation: tool({
    description: "Zakoncz rozmowe z wygenerowanym profilem",
    inputSchema: z.object({
      output: endConversationOutputSchema, // profil odbiorcy
    }),
  }),
  
  flag_inappropriate_request: tool({
    description: "Oznacz nieetyczne lub nielegalne zapytanie",
    inputSchema: z.object({
      reason: z.string(),
    }),
  }),
} as const;
\end{lstlisting}

Dzięki temu podejściu każda odpowiedź AI jest typowana i walidowana schematem Zod, co eliminuje problemy z parsowaniem i zapewnia spójność przepływu danych między mikroserwisami.

\paragraph{Kluczowe problemy i rozwiązania.}
Podczas rozwoju systemu zidentyfikowano i rozwiązano szereg problemów związanych z zachowaniem modeli LLM:

\begin{itemize}
    \item \textbf{Za krótkie rozmowy:} Początkowy prompt generował tylko 10 pytań, co dawało niewystarczające dane. Rozwiązanie: dodanie licznika pytań i wymuszenie minimum 30 pytań przed zakończeniem wywiadu.
    \item \textbf{Pytania w 2. osobie:} Model pytał ,,Czy lubisz gotować?'' zamiast ,,Czy ON/ONA lubi gotować?''. Rozwiązanie: explicite reguła w prompcie wymuszająca 3. osobę.
    \item \textbf{Zbyt abstrakcyjne pytania:} Pytania typu ,,Jaki styl preferuje?'' nie prowadziły do konkretnych kategorii produktów. Rozwiązanie: podejście produktowe -- ,,Czy ma dobre słuchawki?'' zamiast ,,Jaki rodzaj muzyki lubi?''.
    \item \textbf{Brak różnorodności:} Model zawsze zaczynał od pracy zawodowej. Rozwiązanie: lista 16 obszarów eksploracji z wymogiem pokrycia min. 5 różnych.
    \item \textbf{Drążenie po ,,nie wiem'':} Model kontynuował ten sam wątek mimo braku wiedzy użytkownika. Rozwiązanie: reguła natychmiastowej zmiany obszaru po odpowiedzi ,,nie wiem''.
    \item \textbf{Brakujące tool calls:} Model czasami odpowiadał tekstem zamiast wywołać narzędzie. Rozwiązanie: mechanizm auto-retry z przypomnieniem w kolejnej wiadomości.
\end{itemize}

\paragraph{Struktura prompta wywiadu.}
Największy prompt (Chat) liczy ponad 700 linii i wykorzystuje format XML dla lepszej czytelności przez model. Listing~\ref{lst:prompt-structure} przedstawia uproszczoną strukturę tego prompta.

\begin{lstlisting}[caption={Struktura prompta wywiadu z użytkownikiem (uproszczony)},label={lst:prompt-structure}]
<system>
  <role>Jestes Doradca Prezentowym - prowadzisz rozmowe 
        (15-30 pytan) aby poznac obdarowywanego.</role>
  
  <context>
    <occasion>${occasion}</occasion>
    <conversation_progress>
      <current_question_number>${questionCount}</current_question_number>
      <status>MUSISZ ZADAC PRZYNAJMNIEJ ${30 - questionCount} 
              PYTAN WIECEJ!!!</status>
    </conversation_progress>
  </context>
  
  <critical_rules>
    <rule id="1">JEDNO pytanie na raz, PROSTE, konkretne</rule>
    <rule id="2">TRZECIA osoba (on/ona) - NIGDY druga osoba</rule>
    <rule id="3">Pytaj PRODUKTOWO, nie abstrakcyjnie</rule>
    <rule id="5">Eksploruj MINIMUM 5 ROZNYCH obszarow zycia</rule>
    <rule id="6">"Nie wiem" = NATYCHMIAST zmien watek</rule>
  </critical_rules>
  
  <exploration_leads>
    PRACA, DOM, HOBBY, KULINARIA, TECHNOLOGIA, ZDROWIE,
    PODROZE, MUZYKA, ZWIERZETA, SZTUKA, GAMING, FOTOGRAFIA...
  </exploration_leads>
  
  <tools>
    <tool name="ask_a_question_with_answer_suggestions"/>
    <tool name="end_conversation"/>
    <tool name="flag_inappropriate_request"/>
  </tools>
</system>
\end{lstlisting}

\paragraph{Wyniki optymalizacji.}
Iteracyjne doskonalenie promptów przyniosło wymierne rezultaty:
\begin{itemize}
    \item Liczba pytań w wywiadzie: 10 $\rightarrow$ 30 (3$\times$ więcej danych o odbiorcy),
    \item Obszary eksploracji: 6 $\rightarrow$ 16+ kategorii życia,
    \item Sukces tool calls: $\sim$60\% $\rightarrow$ $\sim$95\% (dzięki auto-retry),
    \item Trafność pierwszej rekomendacji: wzrost do 64\% (First Hit Accuracy).
\end{itemize}

Kluczowym wnioskiem z procesu prompt engineeringu jest znaczenie \textbf{konkretnych przykładów} i \textbf{explicite zakazów} w instrukcjach. Model lepiej rozumie ,,NIE pytaj o budżet'' niż ,,skup się na zainteresowaniach''. Podobnie, podanie 2--3 przykładowych rozmów w prompcie drastycznie poprawia jakość generowanych pytań.

\subsection{Równoległa Agregacja Ofert}
Ze względu na limity API i czas odpowiedzi serwisów e-commerce, zaimplementowano mechanizm równoległego pobierania danych. \texttt{Fetch Microservice} może być uruchamiany w wielu instancjach, z których każda obsługuje innego dostawcę (OLX, Allegro, Amazon, eBay, Okazje). Wyniki są asynchronicznie przesyłane do głównego strumienia zdarzeń, co pozwala na prezentowanie pierwszych ofert użytkownikowi bez czekania na zakończenie przeszukiwania wszystkich źródeł.

Zaimplementowany system został poddany weryfikacji poprzez szereg testów, których przebieg i wyniki opisano poniżej.

\section{Testy}

\subsection{Planowanie testów}
Strategia testowania opierała się głównie na testach manualnych pełnego przepływu użytkownika, uzupełnionych o wybrane testy jednostkowe w obszarach najbardziej wrażliwych. Plan obejmował:
\begin{itemize}
    \item \textbf{Testy automatyczne (zakres celowo wąski):} kilka testów jednostkowych w Stalking Microservice (np. \texttt{StalkingAnalyzeHandler}, \texttt{BrightDataService}) oraz podstawowe szkielety e2e/kontrolerów generowane przez NestJS w pozostałych mikroserwisach. Celem było wychwycenie regresji w logice OSINT i poprawności konfiguracji datasetów; reszta pokrywana manualnie.
    \item \textbf{Testy manualne end-to-end (główny ciężar):}
    \begin{itemize}
        \item Pełny scenariusz wyszukiwania: logowanie, formularz (okazja, budżet, linki), wywiad z chatbotem, oczekiwanie na wyniki (SSE), przegląd i oznaczanie ulubionych, zapis historii.
        \item Scenariusze alternatywne: brak linków społecznościowych, częściowa dostępność źródeł ofert (świadome wyłączanie jednego fetchera), przerwanie/ponowienie rozmowy, brak wyników z jednego sklepu.
        \item Refinement: wybór kilku produktów, uruchomienie kolejnej rundy, weryfikacja, że nowe oferty dochodzą z poprawnym oznaczeniem rundy.
        \item Panel admina i feedback: dodanie opinii (ocena, komentarz, opcjonalne zdjęcia), podgląd agregatów w panelu admina, przegląd opinii dla sesji.
        \item UI/UX: responsywność (desktop/mobile), poprawność komunikatów o postępie („to może potrwać kilka minut”), zachowanie przy dłuższym oczekiwaniu na wyniki.
    \end{itemize}
    \item \textbf{Testy danych i odporności:} ręczne sprawdzenie, jak system reaguje na „trudne” dane wejściowe (np. nietypowe linki, brak profili, długie odpowiedzi w czacie) oraz celowe wyłączanie pojedynczych usług (fetch Allegro) w pilotażu, aby ocenić odporność na częściowe awarie.
\end{itemize}
Testy manualne wykonywano iteracyjnie przy każdej większej zmianie (flow użytkownika, integracje fetch/reranking, UI), a zebrane uwagi wprost zasilały backlog poprawek (np. skrócenie wywiadu, dopisanie komunikatów o długim czasie wyszukiwania, balans źródeł ofert). Automatyzacja została ograniczona do najważniejszych fragmentów logiki, a główny nacisk położono na ręczną weryfikację doświadczenia użytkownika i komunikatów w sytuacjach brzegowych.

\subsection{Testy z użytkownikami}
Ważnym elementem weryfikacji jakości systemu były beta-testy z udziałem rzeczywistych użytkowników. Zebrano opinie dotyczące trafności rekomendacji (oceny gwiazdkowe, komentarze tekstowe) oraz wrażeń z korzystania z interfejsu (czas oczekiwania, przejrzystość, intuicyjność). Dane te zostały wykorzystane zarówno w sekcji wyników, jak i przy planowaniu dalszego rozwoju (np. dodanie pamięci negatywnej, lepsze dopytywanie o budżet).

\subsubsection*{Scenariusz testu z użytkownikami}
Każdy uczestnik badania przechodził przez ten sam, ustandaryzowany scenariusz testowy:
\begin{enumerate}
    \item \textbf{Wybór kontekstu:} Uczestnik wybierał realną osobę, dla której w najbliższym czasie planował kupić prezent (np. partner, przyjaciel, członek rodziny), określał okazję (urodziny, święta, rocznica itp.) oraz przybliżony budżet.
    \item \textbf{Konfiguracja wyszukiwania:} Uczestnik wypełniał formularz startowy w aplikacji, podając — jeśli posiadał — linki do profili społecznościowych tej osoby oraz ustawiając budżet zgodnie z założeniami testu.
    \item \textbf{Wywiad z chatbotem:} Uczestnik odpowiadał na kolejne pytania chatu, starając się udzielać pełnych odpowiedzi. Celem było doprowadzenie wywiadu do naturalnego zakończenia (bez świadomego przerywania konwersacji).
    \item \textbf{Analiza rekomendacji:} Po zakończeniu wywiadu uczestnik przeglądał listę zaproponowanych produktów, porównując je z własną wiedzą o obdarowywanym (styl, zainteresowania, posiadane już przedmioty).
    \item \textbf{Ocena całego procesu:} Uczestnik oceniał ogólne doświadczenie z systemem (czas oczekiwania, przejrzystość, intuicyjność, trafność rekomendacji) w formie oceny gwiazdkowej oraz krótkiego komentarza.
    \item \textbf{Ocena pojedynczych produktów (opcjonalnie):} Uczestnik mógł wskazać wybrane produkty i wystawić im osobne oceny (np. które propozycje były szczególnie trafione, a które całkowicie nietrafione), co pozwalało lepiej zrozumieć jakość selekcji.
\end{enumerate}

Jednym z głównych ryzyk, które miały wychwycić testy z użytkownikami, była odporność systemu na częściowe awarie integracji z serwisami e-commerce. W kilku sesjach celowo wyłączono jedną z instancji \texttt{Fetch Microservice} (np. odpowiedzialną za Allegro), aby sprawdzić, czy użytkownik nadal otrzyma sensowny zestaw propozycji z pozostałych źródeł i czy interfejs poprawnie komunikuje ograniczoną dostępność wyników.

W ramach testów szczególną uwagę zwrócono na scenariusz użytkownika szukającego prezentu dla fotografa–amatora. System zaproponował m.in. analogowy aparat z OLX, zestaw akcesoriów do aparatu oraz kurs fotografii online, a użytkownik ocenił całą sesję na 5/5 gwiazdek, podkreślając, że sam nie wpadłby na część tych pomysłów.

Pozytywne wyniki testów pozwoliły na przeprowadzenie badań z użytkownikami końcowymi, których rezultaty przedstawiono w ostatniej sekcji.

    \item Użytkownicy docenili szybkość działania i naturalność konwersacji
\end{enumerate}

\subsection{Stabilność}
System osiągnął 100\% dostępności (uptime) podczas testów, przy minimalnym zużyciu zasobów (<800MB RAM dla całego klastra), co potwierdza poprawność założeń architektonicznych.

\section{Podsumowanie projektu}

AI Present Finder zrealizował cel postawiony na początku przedsięwzięcia: połączył analizę publicznych danych (OSINT), konwersacyjny wywiad z użytkownikiem oraz agregację ofert z wielu platform e-commerce w spójny, działający system rekomendacji prezentów. Z perspektywy użytkownika końcowego aplikacja sprowadza się do prostego procesu: podaj kontekst (okazja, osoba, budżet), porozmawiaj chwilę z AI, a następnie przejrzyj konkretną listę propozycji, które „mają sens” dla danej osoby.

Z perspektywy architektury udało się zrealizować pełny, produkcyjny układ mikroserwisów: od bramy RestAPI (NestJS, JWT, Google OAuth), przez Stalking Microservice (BrightData, OSINT), Chat Microservice (LLM + tool calling), Gift Ideas i Fetch (równoległe pobieranie ofert z wielu źródeł), aż po Reranking Microservice oparty na modelu Gemini 2.5 z wyjaśnialnym scoringiem. Komunikacja asynchroniczna (RabbitMQ) i streaming SSE pozwoliły utrzymać dobrą ergonomię pracy użytkownika mimo wieloetapowego procesu „pod spodem”.

Z punktu widzenia wyników pilotażu system spełnił najważniejsze założenia: średni czas znalezienia prezentu skrócono z rzędu kilkunastu godzin rocznie do pojedynczej sesji trwającej około 7 minut i 44 sekund, przy zachowaniu wysokiej trafności pierwszej rekomendacji (64\%) oraz skutecznym odfiltrowaniu około 40\% szumu ofertowego przez moduł rerankingu. Jednocześnie utrzymano wysoką stabilność techniczną — w trakcie testów nie odnotowano przerw w dostępności aplikacji, a zużycie zasobów pozostało na poziomie akceptowalnym dla środowiska chmurowego.

Zespół przeszedł pełny cykl życia projektu: od POC i weryfikacji ryzyk technologicznych, przez fazę projektowania (diagramy C4, BPMN, model danych), implementację i testy, aż po pilotaż produkcyjny z rzeczywistymi użytkownikami. Ostateczna dokumentacja (niniejszy dokument, raport, diagramy i opisy flow użytkownika) odzwierciedla nie tylko stan końcowy systemu, ale też przyjętą filozofię projektowania: łączenie pragmatycznej inżynierii z czytelną komunikacją „co” i „dlaczego” zostało zrobione.

\section{Wnioski i kierunki dalszego rozwoju}

Wdrożenie AI Present Finder pozwoliło w praktyce zweryfikować założenia tzw. \textit{Agentic Commerce}: dużą część procesu decyzyjnego przy wyborze prezentu można przekazać autonomicznemu agentowi AI, który sam zbiera kontekst, przeszukuje rynek i selekcjonuje oferty. Analiza wyników, feedbacku użytkowników i doświadczeń zespołu prowadzi do kilku nadrzędnych wniosków:
\begin{itemize}
    \item \textbf{Połączenie OSINT + wywiad AI działa.} Użytkownicy docenili fakt, że system „zna kontekst” — łączenie publicznych profili z rozmową pozwala generować rekomendacje bliższe realnym zainteresowaniom obdarowywanej osoby niż klasyczne filtry typu kategoria/cena.
    \item \textbf{Reranking z uzasadnieniami ma dużą wartość dodaną.} Moduł oceniający produkty z komentarzem AI skutecznie usuwa oferty przypadkowe, skracając listę do propozycji, które faktycznie da się rozważyć. Jednocześnie taki sposób działania jest łatwy do audytu i dalszego strojenia.
    \item \textbf{Streaming i asynchroniczność są konieczne przy długich procesach.} Pełne wyszukiwanie (OSINT, kilkaset produktów z wielu sklepów, reranking) może trwać kilka minut, ale dzięki SSE użytkownik na każdym etapie widzi, że system pracuje i stopniowo dostaje wyniki. To podejście okazało się niezbędne dla utrzymania zaangażowania.
    \item \textbf{Największe ograniczenia leżą po stronie danych.} Główne problemy zgłaszane w badaniu (polecanie rzeczy, które dana osoba już posiada, oraz bias w stronę jednego źródła ofert) wynikają z brakującej „pamięci negatywnej” i nierównomiernej dostępności danych z poszczególnych platform.
\end{itemize}

Na tej podstawie można wskazać naturalne kierunki dalszego rozwoju systemu:
\begin{itemize}
    \item \textbf{Pamięć negatywna i lepsze modelowanie historii.} Dodanie mechanizmów zapamiętywania produktów już posiadanych oraz prezentów odrzuconych przez użytkownika pozwoli ograniczyć polecanie „tych samych rzeczy” i jeszcze lepiej wykorzystać zebrany feedback.
    \item \textbf{Balansowanie i rozszerzanie źródeł ofert.} Z punktu widzenia użytkownika ważne jest, aby lista prezentów była różnorodna zarówno pod względem rodzaju produktów, jak i źródeł (nowe vs. używane, różne platformy). W praktyce oznacza to dalszą pracę nad integracjami oraz logiką ważenia źródeł.
    \item \textbf{Optymalizacja czasu reakcji i kosztów.} Choć obecny czas do wyników jest akceptowalny w kontekście pilotażu, celem kolejnego etapu jest dalsze skrócenie opóźnień (docelowo do kilku minut lub mniej) przy utrzymaniu lub obniżeniu kosztów operacyjnych, m.in. poprzez lepsze wykorzystanie streamingu, cache i odpowiednio dobrane modele.
    \item \textbf{Wyszukiwanie wektorowe i rekomendacje oparte na feedbacku.} Dodanie wyszukiwania semantycznego (embeddingi) oraz mechanizmów uczących się z ocen użytkowników pozwoliłoby wychodzić poza prostą filtrację ofert i stopniowo „dostrajać” system do preferencji społeczności używającej aplikacji.
    \item \textbf{Wywiad adaptacyjny i personalizacja interfejsu.} Zebrane opinie pokazują, że część użytkowników chciałaby krótszych lub bardziej „na temat” rozmów. Naturalnym kierunkiem jest dalsze upraszczanie dialogu oraz dopasowanie interfejsu do mniej technicznych użytkowników.
    \item \textbf{Eksploracja modelu biznesowego.} Przy zachowanych parametrach jakości i stabilności AI Present Finder może stanowić bazę pod komercyjne rozwiązanie (np. model afiliacyjny, integracje dla sklepów, wersja Pro dla agencji marketingowych). Obecne MVP pokazuje, że technicznie jest to wykonalne.
\end{itemize}

Podsumowując, projekt AI Present Finder potwierdził, że połączenie OSINT, konwersacyjnego AI i świadomie zaprojektowanej architektury mikroserwisowej pozwala realnie poprawić doświadczenie kupowania prezentów. Jednocześnie wskazał, że kluczem do dalszego wzrostu jakości nie są już tylko „mocniejsze modele”, lecz przede wszystkim bogatsze dane, lepsze wykorzystanie feedbacku użytkowników i dopracowanie doświadczenia końcowego odbiorcy.
